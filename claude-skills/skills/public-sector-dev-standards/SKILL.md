# 공공기관 납품용 개발 기준 스킬

## 1. 착수 전 확인
- 과업지시서·제안요청서의 기능·비기능 요구사항(보안, 성능, 접근성, 호환성, 표준프레임워크 적용 여부)을 먼저 읽는다. 있으면 그것이 이 스킬보다 우선한다.
- 요구사항마다 ID를 붙이고(예: SFR-001), 설계·코드·테스트까지 추적할 수 있게 요구사항 추적표를 유지한다.
- 운영 환경: 시 전산실·클라우드(공공 클라우드 보안인증 등) 여부, 망분리, 브라우저·OS 지원 범위.

## 2. 개발 원칙
- 설계 먼저: 기능 목록 → 화면 설계 → 데이터 모델 → 인터페이스 → 구현. 변경은 작게 나누고 단계마다 검증한다.
- 필요 이상으로 복잡하게 만들지 않는다. 외부 라이브러리는 라이선스와 유지보수 상태를 확인하고 목록을 문서화한다(공개 SW 라이선스 의무 포함).
- 코드 컨벤션·린트·포맷터를 팀 기준으로 고정하고, Git은 기능 브랜치 + 코드 리뷰 후 병합.

## 3. 보안 (리뷰 때 가장 먼저 본다)
- 행정안전부 소프트웨어 보안약점 기준을 따른다: 입력값 검증(SQL 삽입, XSS, 경로 조작, 명령 삽입), 인증·권한 확인, 암호화, 에러 메시지로 내부 정보 노출 금지, 세션 관리.
- 비밀번호·API 키·DB 접속 정보는 코드·저장소에 넣지 않는다(환경변수·비밀 관리 도구).
- 외부 서비스로 데이터를 보내는 기능은 발주처 승인 범위를 확인한다.

## 4. 개인정보
- 개인정보 보호법 기준으로 최소 수집, 목적·보유기간 명시, 고유식별정보·비밀번호 등 암호화, 접근 기록 보관.
- 테스트에는 실제 개인정보를 쓰지 않고 가명·더미 데이터를 쓴다.

## 5. 접근성·호환성
- 웹은 한국형 웹 콘텐츠 접근성 지침(KWCAG)을 따른다: 대체 텍스트, 명도 대비, 키보드 접근, 레이블·오류 안내, 제목 구조.
- 지정된 브라우저·모바일 환경에서 동작을 확인한다.

## 6. 테스트와 품질
- 단위 → 통합 → 인수 테스트. 정상·경계·예외 케이스를 각각 두고, 결과를 테스트 결과서로 남긴다.
- 성능 요구가 있으면 응답시간·동시접속 기준을 수치로 검증한다.

## 7. 납품 산출물
요구사항 정의서, 요구사항 추적표, 화면·테이블 설계서, 인터페이스 정의서, 테스트 계획·결과서, 보안약점 점검 결과, 설치·운영자·사용자 매뉴얼, 공개 SW 목록, 소스코드. 과업지시서가 정한 목록이 있으면 그것을 따른다.

## 코드 리뷰 출력 형식
심각도 순(보안·개인정보 → 기능 오류 → 성능 → 유지보수성)으로, 각 항목에 위치·문제·영향·수정 예시를 적는다.
